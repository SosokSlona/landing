1. Исходная проблема и вызовы инфраструктуры

В высоконагруженных B2B-системах подключение клиентов напрямую к инференс-серверам (vLLM / TGI) приводит к фатальным отказам. В отличие от стандартных веб-сервисов, инференс больших языковых моделей обладает критическими свойствами:

  • Ограниченность контекстной памяти (KV Cache): неконтролируемый наплыв параллельных длинных промптов мгновенно приводит к исчерпанию VRAM (CUDA Out Of Memory).
  • Неприменимость классического Rate Limiting (RPS): один запрос на 4,000 токенов нагружает GPU сильнее, чем 100 запросов по 20 токенов. Ограничивать необходимо именно Tokens Per Minute (TPM) и активный KV-cache volume.
  • Потоковая деградация (Streaming SSE): клиенты держат постоянное HTTP-соединение, что при блокирующей архитектуре исчерпывает файловые дескрипторы и пулы потоков.

3. Алгоритм Token Bucket в Redis на базе атомарного Lua

Для предотвращения Race Condition при миллионах запросов резервирование квот по пользователю и организации выполняется за один атомарный round-trip в Redis.

token_bucket_limiter.lua Atomic Execution 
local key = KEYS[1]
local requested_tokens = tonumber(ARGV[1])
local capacity = tonumber(ARGV[2])
local fill_rate = tonumber(ARGV[3])
local now = tonumber(ARGV[4])

local data = redis.call("HMGET", key, "tokens", "last_update")
local current_tokens = tonumber(data[1])
local last_update = tonumber(data[2])

if not current_tokens then
  current_tokens = capacity
  last_update = now
else
  local elapsed = math.max(0, now - last_update)
  current_tokens = math.min(capacity, current_tokens + (elapsed * fill_rate))
end

if current_tokens >= requested_tokens then
  current_tokens = current_tokens - requested_tokens
  redis.call("HMSET", key, "tokens", current_tokens, "last_update", now)
  redis.call("EXPIRE", key, math.ceil(capacity / fill_rate) * 2)
  return {1, math.floor(current_tokens)}
else
  return {0, math.floor(current_tokens)}
end

4. Оптимизация задержек: стриминг без аллокаций

Для минимизации Time To First Token (TTFT) проксирование SSE (Server-Sent Events) реализовано через кастомный `io.Reader` пайплайн с пулом буферов `sync.Pool`. Пакеты токенов сбрасываются клиенту сразу через `http.Flusher` без промежуточного декодирования JSON.

Результат: дополнительная задержка прокси-слоя составила менее 1.8 миллисекунд при нагрузке 8,500 одновременных активных стримов на ноду.
